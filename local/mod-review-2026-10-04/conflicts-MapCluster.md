## Findings and owner decisions

### 1. ServerSideMap + Huginn_Map — OVERLAP, not proven mutually exclusive/crashing

Both implement world/server-wide explored-map sharing. ServerSideMap README `D/Mydayyy-ServerSideMap-1.3.14/README.md:3-8,45-49` explicitly merges every participating client's exploration and distributes it to connected clients. Huginn README `R/NightOfGames__Huginn_Map.md:6-12` says everyone sees anyone's exploration. These are not guild-scoped maps. Turning Huginn `ShareVanillaPins` off prevents vanilla pin sharing, **not fog sharing** (`R/...:64`).

Patch distinction matters: ServerSideMap patches `Minimap.Explore(Vector3,float)` and `Explore(int,int)` (`C(Mydayyy-ServerSideMap-1.3.14,ServerSideMap):157-171,432-449`); Huginn periodically calls `GetSharedMapData(null)` / `AddSharedMapData`, and prefixes `AddSharedMapData` with an exploration-only merge when vanilla pin sharing is off (`C(NightOfGames-Huginn_Map-1.0.6,Huginn):1004,1014-1049,2902-2956`). Thus claiming they both fight an identical Explore prefix would be incorrect. They have independent canonical-map stores and redundant propagation; bad interaction is [INFERENCE], not a verified hard failure.

**Decision / recommendation:** for competing guilds remove both. If the owner wants cooperative world-wide geography instead, choose exactly one; Huginn bundles the shared auto-pin registry, while ServerSideMap is the narrower fog-sharing choice with BetterMap retained for local pins. Never interpret either as per-guild privacy.

### 2. BetterMap + Huginn + ExpertExplorer pinning — OVERLAP

BetterMap auto-pins ores, harvestables, dungeons and portals (`R/xtavim__BetterMap.md:31-37,51-53,93-105`). Huginn auto-pins the same categories, plus shared cleared status (`R/NightOfGames__Huginn_Map.md:14-26`). ExpertExplorer defaults `Auto-Pin Dungeon Locations=true` (`C(MilkMediaProductions-ExpertExplorer-1.7.0,ExpertExplorer):506`) and offers manual discovery pinning. Different deletion semantics matter: BetterMap deleted pins stay deleted; Huginn has whole-server crossed-out status and depletion removal. BetterMap's defaults scan 100 m; Huginn scans ore/pickables at 10 m and POIs at 30 m (respective README lines 99 and 53-54). BetterMap is also creature radar, not just QoL.

**Decision / recommendation:** choose one owner for automatic resource/dungeon/portal pins. For recommended private exploration: retain ExpertExplorer as the progression system, turn its dungeon auto-pin off if BetterMap does that job, and set BetterMap `Show Creatures=false`, `Reveal Traders=false`, reduce `Pin Radius` substantially or disable automatic resource pins. This preserves ambush/difficulty and finding locations rather than sweeping 100 m around corners. For global option A: Huginn owns auto pins; disable BetterMap auto-pins and portal pins, preferably omit BetterMap entirely. [INFERENCE] Duplicate visible icons depend on pin/icon merging and load order; no universal crash established.

### 3. ZenMap + ExpertExplorer — HARD conflict (source-proven competing radius semantics)

ZenMap opening a table/map item sets it active, calls `Minimap.Reset()`, then `Minimap.Explore(Position, Radius)` (`C(ZenDragon-ZenMap-1.11.0,ZenMap):1408-1414`). ExpertExplorer's prefix on that exact overload **replaces the passed radius** with `Mathf.Lerp(m_exploreRadius, MaxExploreRadius, skill/100)` regardless of caller; only its Sailing integration bypasses this (`C(MilkMediaProductions-ExpertExplorer-1.7.0,ExpertExplorer):1100-1114`). ZenMap table defaults are 1250 m and age-based; ExpertExplorer default skill maximum is 200 m (`R/ZenDragon__ZenMap.md:303-313`; ExpertExplorer code:503). So ExpertExplorer converts ZenMap table/chart area into player-skill radius. This is a behavior conflict, not a crash claim.

**Decision / recommendation:** do not combine. If option C is chosen, omit ExpertExplorer rather than promising its exploration-radius progression survives nomap. There is no verified config switch that disables just this prefix.

### 4. ZenMap + global fog mods / BetterMap — HARD map-model conflict for fog; OVERLAP/INTERACTION for pins

ZenMap declares character exploration will reset (`R/ZenDragon__ZenMap.md:9-13`), table age replaces character exploration (`:21-27`), and manually adding pins in map view is replaced by world signs (`:74-108`). Its reset clears **both** `m_explored` and `m_exploredOthers` (`C(ZenDragon-ZenMap-1.11.0,ZenMap):987-996`), then explores the active table radius. A global sharing mod reintroduces world-wide fog into that same state, while ServerSideMap sees the synthetic table Explore calls as exploration to propagate. [INFERENCE] Exact timing determines visible leakage/reset churn, but the stores have contradictory ownership; do not combine ZenMap with either global-fog mod.

BetterMap's `UpdateExplore` prefix sets `m_exploreRadius` (`C(xtavim-BetterMap-1.1.0,BetterMap):1024-1027`), whereas ZenMap conditionally suppresses original `UpdateExplore` while its location map is in use (`C(ZenDragon-ZenMap-1.11.0,ZenMap):4906-4911`). Same target alone is not proof of hard conflict: those two prefixes do not themselves both set the same radius. The actual issue is redundant creature/vehicle/resource/portal pin production plus ZenMap's replacement visibility/pin model; compatibility of arbitrary BetterMap pins on ZenMap tables was not runtime-verified. **Recommendation:** omit BetterMap for option C, rather than maintaining two map owners.

### 5. Guilds + ServerSideMap marker sharing — HARD privacy/patch conflict when marker sharing is enabled

Both patch `Minimap.OnPinTextEntered`. Guilds captures a `!` pin and converts it to a guild RPC (`C(Northarun-Guilds-1.2.2,Guilds):10076-10077,10274-10275`). ServerSideMap independently captures `m_namePin` in a prefix and sends that captured pin server-wide in a postfix (`C(Mydayyy-ServerSideMap-1.3.14,ServerSideMap):790-807`); the server receives it into the shared registry (`:815-826`). [INFERENCE] Exact text/removal state depends on Harmony postfix ordering, but there is no guild filter in this interception. Turning marker sharing on risks exporting the very pin the owner meant to keep guild-only.

**Decision / recommendation:** keep `General.EnableMarkerShare=false` or remove ServerSideMap. Guilds alone should own `!` pins. Huginn `Map.ShareVanillaPins=false` similarly avoids deliberate global vanilla-pin copying; its resource/boat/portal registry is still global. Do not claim that this switch makes Huginn per-guild.

### 6. Guilds + Venture position settings — INTERACTION, a useful split of responsibilities

Guilds explicitly shows members even with hidden public position (`R/Northarun__Guilds.md:108-109`), and its code adds private member pins from guild RPC positions (`C(Northarun-Guilds-1.2.2,Guilds):10114-10152`). Guild pins are stored under the sender's guild with permission checks, not a world bucket (`:5473-5511`), and broadcast iterates guild members (`:5461-5464`). These are member positions and shared pins, **not shared fog**: no per-guild fog feature is documented or identified in this map integration.

Venture controls public position with actual config keys `Map.OverridePlayerMapPositions` and `Map.ForcePlayerMapPositionOn` (`C(VentureValheim-Venture_Multiplayer_Tweaks-1.0.0,VentureValheim.MultiplayerTweaks):329-332,480-482`). Its README uses older names `OverridePlayerMapPins` (`R/VentureValheim__Venture_Multiplayer_Tweaks.md:77`); prefer assembly bindings for 1.0.0. **Recommendation:** force public position off (`OverridePlayerMapPositions=true`, `ForcePlayerMapPositionOn=false`), keep Guilds `ShareMemberPositions=true`, and choose public ping policy deliberately. `AllowShoutPings=false` avoids login/shout location giveaways; `AllowMapPings=false` avoids public pings. README compatibility claim is about **Groups**, not Northarun/Guilds (`:83`), so private Guilds-ping compatibility must not be assumed.

### 7. ZenMap + Guilds / Venture — HARD workflow incompatibility for ! pin creation; INTERACTION for positions

ZenMap blocks `ShowPinNameInput` while viewing its location map (`C(ZenDragon-ZenMap-1.11.0,ZenMap):4892-4897`). Guilds `!` sharing depends on `OnPinTextEntered`; the ordinary supported GUI creation workflow is therefore unavailable on ZenMap tables/items. ZenMap sign pins are private per player, not guild pins (`R/ZenDragon__ZenMap.md:100-108`). [INFERENCE] An alternate code-injected pin might render, but that is not a supported guild-map workflow.

ZenMap public tracking is also not secrecy by default: tables expose tracked ships/carts/tombstones to everyone (`:58-60,82-92`), player positions ordinarily show unless PvP (`:84`), and anyone can view a table unless access is physically warded (`:83`). **Recommendation:** if option C, disable Guilds map positions (`ShareMemberPositions=false`), set `MaxGuildPins=0`, let ZenMap own all map/ping/position presentation, remove Player and movable/death tracking from `Show - Table` as appropriate. This is restricted-access local charts, not cryptographically per-guild data.

### 8. Seasonality + maps — no verified direct Minimap/fog-sync conflict

Whole Seasonality assembly search found no `Minimap` reference/patch. It does patch `Heightmap.GetBiomeColor` and remaps terrain colours in winter/fall (`C(RustyMods-Seasonality-3.8.3,Seasonality):1474-1497`). ZenMap README warns to disable seasonal minimap recolouring when hiding map biomes (`R/ZenDragon__ZenMap.md:366-375`), but that comment refers to a generic **Seasons mod**, not a confirmed Seasonality setting. No corresponding recolour-minimap key was found in Seasonality 3.8.3 or `config/enforced/RustyMods.Seasonality.cfg`. **Recommendation:** do not invent a Seasonality minimap toggle or declare a hard conflict; seasonal map appearance with ZenMap is a visual-runtime coverage gap. `Calendar Days Per Year` can be aligned to the chosen seasonal year length, but does not synchronize fog (`R/...:347-355`).

### 9. AzuHoverStats / AzuClock — INTERACTION with information difficulty, not map duplication

Repository records AzuHoverStats as client-only, no synced settings, and its container readout respects private-area access (`docs/modstack.md:47,154,361-366`). It gives creature/container/crafting information rather than explored fog. AzuClock gives weather/time information (`docs/modstack.md:48,155`). **Decision / recommendation:** keep as optional client information tools if desired; do not describe them as server-enforced difficulty controls. BetterMap creature radar is a materially stronger information advantage because it locates nearby threats on the map, and should be server-disabled in option B. Exact HoverStats per-readout option names were not needed to establish this boundary and are not verified here.

## Coherent options A / B / C

### A — Cooperative world atlas

Choose this if everyone should benefit instantly from every guild's scouting. **One** shared fog system: Huginn alone for global fog + curated low-radius auto pins, or ServerSideMap alone for fog with BetterMap handling local pins. No ZenMap. Guilds remains useful for private member positions and intentional `!` notes, but public auto resource/portal/boat pins are consciously not private. Keep Huginn `ShareVanillaPins=false` / ServerSideMap `EnableMarkerShare=false` to avoid importing private notes. If Huginn owns auto pins, remove BetterMap and disable ExpertExplorer dungeon auto-pins. ExpertExplorer can remain for personal XP/radius; its scout reveals then benefit everyone, reducing exclusive scout value. This option is least aligned with discovery/competition because explored corridors and communal boat/portal pins expose where other groups have been.

### B — Private exploration + guild coordination (**recommended**)

Remove ServerSideMap and do not add Huginn or ZenMap. Keep ordinary character fog and ExpertExplorer exploration progression. Guilds owns private member positions and deliberate `!` pins; set Venture public map positions forced off, shout/public pings off, and use voice/chat or intentional table sharing for cross-guild cooperation. Retain BetterMap only with creature radar disabled, trader reveal off, modest automatic-pin radius or auto-pin disabled; one dungeon pin owner. Guild tables can be physically access-controlled for intentional map sharing. **Important limitation:** this is personal explored fog + per-guild pins/positions + voluntary cartography, not automatic per-guild explored-fog synchronization. None of the reviewed mods supplies the latter. This is the strongest fit for distance making encounters meaningful while giving scouts progression and guildmates practical coordination.

### C — Nomap / regional charts as an exploration economy

ZenMap owns map presentation, table-age survey, sign markers and parchment progression. Remove both global sharing systems, BetterMap and ExpertExplorer. Disable Guilds map positions/! pins rather than advertising a broken GUI. Keep Artisan-stage parchment or choose an earlier station explicitly; table radius/age and map crafting become exploration progression. Restrict table access through wards/doors; do not leave globally visible Player/ship/cart/tombstone tracking on if strategic secrecy is intended. Tables expose nearby geography without the explorer personally walking it, so this is regional chart surveying rather than private exploration skill. Character backups are mandatory before migration because README says exploration resets. More immersive and navigation-heavy, but larger change and less progression-compatible than B.

## Coverage gaps / claims not made

- No runtime coexistence, visual rendering, reconnect or handshake scenario exercised; no crash assertions. Read-only research supports patch/model conflicts and identifies a concrete radius override, not a tested production deployment.
- True automatic per-guild fog is absent in the reviewed feature/API surfaces; implementing it would be new work, not an available config.
- Expanded-world map-size compatibility needs a targeted runtime scenario: ServerSideMap hardcodes map size 2048 and 4194304 cells (`code:178-193`), while Huginn merge uses `m_textureSize` (`code:2938-2946`). ZenMap has `Compatibility.Zoom Scale`. Current enforced Expand World file search found no map-size/pixel key; do not claim the existing 15000-radius world necessarily has a non-2048 texture or that ServerSideMap definitely breaks it.
- Seasonality visual map-colour behavior and ZenMap's generic Seasons warning do not establish a Seasonality-specific conflict; no verified recolour-minimap option exists here.
- Private notes cannot be made secret after global sharing has already disclosed them; turning off a mod does not erase human knowledge. Character/sidecar backups and reset policy must be decided before any migration [INFERENCE].
- AzuHoverStats individual readout keys and AzuClock handshake internals were not re-decompiled in depth; repo evidence establishes client-only deployment and enforcement boundaries, not every local preference.
