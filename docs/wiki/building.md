# Building plugins and native forks

This page explains how the repository builds its BepInEx plugins and maintained 1.0-native forks, why local reference extraction is a prerequisite, and which diagnostics matter before trusting a build. The build targets the latest stable/public game; recorded development versions are test inputs, not a freeze for the Run (`docs/build.md:3-7`).

## Decisions

**A fresh clone cannot compile the plugins until reference assemblies have been extracted.** `lib/valheim/` and `lib/bepinex/` are gitignored, not supplied by the checkout. Run `scripts/extract-refs.sh` against a local client or dedicated-server installation before `dotnet build`; the shared targets explicitly fail when the game or loader references are missing. The documented clean-checkout route uses `scripts/test-server.sh install`, which obtains the server and invokes extraction (`.gitignore:7-10`; `Directory.Build.targets:3-8`; `docs/build.md:47-65`).

- **Discover projects rather than maintain a solution file.** `Valheim.Lembitu.proj` deliberately replaces a `.sln`: adding a plugin or fork should mean adding its directory, not also editing a registry with another GUID. Its `src/**/*.csproj` glob feeds the root `Restore`, `Build` and `Clean` targets; `Rebuild` runs `Clean;Build` (`Valheim.Lembitu.proj:1-27`).
- **Use one shared compilation contract.** Plugins target `net472` for Unity's Mono runtime. `Microsoft.NETFramework.ReferenceAssemblies` 1.0.3 supplies framework references off Windows; the shared properties also enable nullable annotations and portable debug information. `ValheimRefDir`, `BepInExRefDir` and `PluginDistDir` resolve to repository-local reference and output directories (`Directory.Build.props:3-25`).
- **Extract from the game being exercised.** `scripts/extract-refs.sh` prefers the local test server, then SteamCMD server installs, then client installs. `VALHEIM_MANAGED` explicitly selects another Managed directory and must contain `assembly_valheim.dll`. Extraction copies game/Unity assemblies and selected managed dependencies (`scripts/extract-refs.sh:29-39`, `scripts/extract-refs.sh:49-76`, `scripts/extract-refs.sh:174-190`).
- **Pin the extracted bytes, not an assumed game identity.** The generated `lib/valheim/refs.lock.json` records extraction time, source directory, BepInEx pack identity and SHA-256 hashes for the extracted game and loader DLLs. `scripts/extract-refs.sh --check` compares the local copies and, when available, their original game installation (`scripts/extract-refs.sh:20-24`, `scripts/extract-refs.sh:101-119`, `scripts/extract-refs.sh:129-170`).
- **Compile against the loader pack used for deployment.** The extraction script pins `denikson-BepInExPack_Valheim` **5.4.2350** (BepInEx **5.4.23.5**) to SHA-256 `37a91c000b4e88f2ed7a4bd7d812239852d2e36cbf0ff0a9f5faacfba46b105f`. It verifies the downloaded archive, keeps the full pack under `lib/bepinex/pack/`, and copies `BepInEx.dll` and `0Harmony.dll` into the reference directory (`scripts/extract-refs.sh:16-18`, `scripts/extract-refs.sh:78-98`; `docs/build.md:76-78`).
- **Publicize references at build time.** `BepInEx.AssemblyPublicizer.MSBuild` 0.4.3 exposes private members needed by patches. The shared game references opt in through `Publicize` metadata; a plugin adds other references through `$(ValheimRefDir)` and opts in only where needed (`Directory.Build.props:23-42`; `docs/build.md:108-126`).
- **Provide tooling, not game binaries, through Nix.** `nix develop` supplies .NET SDK 8, curl, unzip and zip for x86_64/aarch64 Linux and Darwin. The shell sets `DOTNET_ROOT` and disables CLI telemetry. Without Nix, the build guide permits .NET SDK 8 or newer; Windows or Mono need not be installed to compile (`flake.nix:8-25`; `docs/build.md:64-65`).
- **Generate identity and collect outputs centrally.** Each plugin declares its GUID and version in its project; `GeneratePluginInfo` emits the compile-time constants rather than duplicating identity in source. `CopyPluginToDist` copies each built DLL to `dist/plugins/` and registers it for cleaning. Root `Clean` removes that entire plugin output directory, including stale DLLs from renamed or deleted projects. Staging adopted mods is a separate step that populates the broader `dist/{plugins,patchers,config}/` installer tree (`Directory.Build.targets:10-42`; `Directory.Build.props:7`; `Valheim.Lembitu.proj:21-27`; `docs/build.md:20-22`, `docs/build.md:54-55`).

## Exclusions

- **No checked-in extracted binaries or build products.** Game and BepInEx assemblies are local inputs reproduced by extraction, not repository contents. The ignore rules cover `lib/valheim/`, `lib/bepinex/`, `lib/.cache/`, `bin/`, `obj/` and `dist/`; the generated reference lock therefore lives with ignored local inputs, not as a committed dependency lock (`docs/build.md:20-27`; `.gitignore:1-10`; `scripts/extract-refs.sh:20-24`).
- **No framework DLLs copied from Unity.** Extraction deliberately excludes `mscorlib`, `netstandard` and `System.*`: NuGet supplies the net472 framework references, and combining both sets produces duplicate-type errors. Game and loader references use `Private="false"`, keeping those assemblies out of plugin output because the server already supplies them (`scripts/extract-refs.sh:26-39`; `Directory.Build.props:27-56`).
- **No standalone ServerSync plugin.** `src/forks/ServerSync/` is a source-library fork with no `.csproj` or separate DLL. Consumers import `ServerSync.props` to compile it into their own plugin (`src/forks/README.md:34-37`).
- **No automatic build of adopted mods.** Root compilation discovers source projects; adopted packages are staged separately. Own plugins and forks remain separate so source ownership and licensing stay visible (`Valheim.Lembitu.proj:9-18`; `docs/build.md:54-55`; `src/forks/README.md:3-5`).

## Lessons

- **Intact references can still be stale.** Valheim version constants are inlined into plugin DLLs; a game update does not change an already compiled value. The build guide records this failure in pre-1.0 ServerSync on 1.0.7 and identifies `Lembitu.Hello` as a skew diagnostic. Re-extract and rebuild after an update. If the source installation is absent, `--check` reports that local references are intact but game drift is unchecked; that is not proof of compatibility with another installation (`docs/build.md:80-87`; `scripts/extract-refs.sh:150-165`).
- **A missing-reference error is an extraction prerequisite, not a compiler fix.** Check the Managed-directory selection and run extraction; an invalid `VALHEIM_MANAGED` or no discovered installation produces an explicit error before copying (`Directory.Build.targets:3-8`; `scripts/extract-refs.sh:49-76`).
- **Publicizer syntax matters.** Put `Publicize` metadata on the `Reference`; a separate `Publicize` item acquires empty default metadata that its task rejects (`docs/build.md:123-126`).
- **Broad Unity references need exclusions.** EpicMMOSystem uses a wildcard rather than maintaining a large module list, but excludes shared references to avoid duplicates. `UnityEngine.ImageConversionModule` is also excluded: it targets netstandard 2.1 and causes CS1705 for net472 (`src/forks/EpicMMOSystem/EpicMMOSystem.csproj:49-59`; `docs/build.md:128-139`).
- **Preserve upstream code rather than rewriting it to silence nullable warnings.** Forks use `Nullable=annotations`; disabling annotations instead reports imported ServerSync's `?` annotations as CS8632. Recorded successful builds still had 13 existing fork warnings, so historical success is not a claim of a warning-free build (`src/forks/README.md:20-27`; `docs/build.md:663-666`).
- **Compile-time library resolution does not prove runtime binding.** Strong-named .NET Framework libraries bind by exact assembly version. The YamlDotNet Thunderstore package numbered 16.3.1 contains library 16.3.0; the fork therefore pins `[16.3.0]` and excludes runtime assets rather than floating to a newer incompatible library or shipping another copy (`src/forks/ItemRequiresSkillLevel/ItemRequiresSkillLevel.csproj:19-26`; `docs/build.md:141-155`).
